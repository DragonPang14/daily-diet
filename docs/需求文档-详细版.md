# 每日饮食助手 —— 详细需求文档

> 版本：v1.0
> 更新：2026-10-13
> 状态：草稿

***

## 一、产品概述

### 1.1 产品定位

一款面向健身人群（尤其是力量训练者）的轻量化饮食管理小程序。核心价值：**智能推荐 + 极简操作 + 可替换食材**。

| 竞品   | 主要痛点                           | 本产品的差异化                |
| ---- | ------------------------------ | ---------------------- |
| 持续进步 | 操作简单但无自动推荐、广告/弹窗过多、非饮食功能（训练）冗余 | 专注饮食单一领域，自动推荐食谱        |
| 薄荷健康 | 食物碳蛋脂不可定制、运动消耗粒度粗、收费过高         | 支持自定义食材营养比例替换，推荐可按品牌微调 |

### 1.2 核心问题（原始输入）

1. 记录饮食操作繁琐 —— 每次都要手动选食物+重量
2. 无法自动推荐食谱 —— 市面上产品只提供记录能力，不提供规划能力
3. 无法灵活替换食材 —— 用户不喜欢某食材时（如不吃鸡胸肉），找不到碳蛋脂接近的替代
4. 食物热量不可定制 —— 同一类食物（如全麦面包）不同品牌营养比例差异大

### 1.3 产品目标（Objectives）

| 目标        | 衡量指标              |
| --------- | ----------------- |
| 降低饮食记录门槛  | 每日记录时间 ≤ 60 秒     |
| 提升推荐满意度   | 用户对推荐食谱的采纳率 ≥ 60% |
| 提升食材替换灵活度 | 替换操作完成到出结果 ≤ 3 秒  |

### 1.4 目标用户画像

**主要用户：力量训练者（男性 18-40 岁为主）**

| 维度 | 描述                                            |
| -- | --------------------------------------------- |
| 年龄 | 18-40 岁                                       |
| 特征 | 规律健身（每周 3+ 次力量训练）、关注增肌/减脂、对三大项（深蹲/卧推/硬拉）成绩有概念 |
| 痛点 | 花在「查吃什么」和「记录吃了什么」的时间过多，想要自动化                  |
| 设备 | 微信生态，偶尔 PC                                    |

**次要用户：减脂人群**

无系统训练但有饮食控制需求的用户，关注热量缺口而非肌肉量估算。

## 二、功能需求

### 2.1 功能全景图

```
每日饮食助手
├── 用户模块
│   ├── 微信登录与基础信息（性别 / 年龄 / 身高 / 体重）
│   ├── 训练水平输入（三大项成绩）
│   ├── 目标设置（增肌 / 减脂 / 维持 / 自定义 TDEE）
│   └── 基础代谢（BMR）与每日能量需求（TDEE）自动计算
├── 食谱推荐模块
│   ├── 按目标自动生成日食谱（早 / 午 / 晚 / 加餐）
│   ├── 按用户偏好分配 PFC 比例（碳水 / 蛋白 / 脂肪）
│   ├── 食材一键替换（同 PFC 类型、比例接近）
│   └── 历史食谱保存与收藏
├── 饮食记录模块
│   ├── 推荐食谱一键入库（每日自动标记已食用）
│   ├── 手动添加自定义食物
│   ├── 按餐次修改（克数、替换食材）
│   └── 每日汇总：总热量 / PFC 占比 / 与目标差值
├── 食物库模块
│   ├── 基础食物库（参考《中国食物成分表》第 6 版）
│   ├── 自定义食物（可录入品牌、自定义 PFC）
│   ├── 食物搜索（名称模糊匹配 + 标签过滤）
│   └── 收藏 / 常用食物置顶
└── 统计与反馈
    ├── 近 7 天 / 30 天饮食趋势
    ├── 达成率（实际 vs 目标）
    └── 简易 AI 饮食建议（文字版）
```

### 2.2 用户模块

#### 2.2.1 微信登录

| 项目   | 说明                                             |
| ---- | ---------------------------------------------- |
| 触发   | 首次打开小程序                                        |
| 流程   | `wx.login()` → 拿 code → 后端换 `openid` → 创建/查询用户 |
| 失败兜底 | 登录失败可重试，不阻塞浏览公共内容（食物库）                         |

#### 2.2.2 基础信息录入（Onboarding 第 1 步）

| 字段       | 类型      | 校验规则              | 必填 |
| -------- | ------- | ----------------- | -- |
| 性别       | 枚举（男/女） | 单选                | 是  |
| 生日       | 日期      | 年龄 14-80          | 是  |
| 身高       | 数字      | 120-230 cm        | 是  |
| 当前体重     | 数字      | 30-200 kg，精确到 0.1 | 是  |
| 目标体重（可选） | 数字      | 合理范围              | 否  |

#### 2.2.3 训练水平录入（Onboarding 第 2 步）

> 用于估算肌肉量，进而修正 BMR。若用户不填，则使用 Mifflin-St Jeor 公式的普通人群版本。

| 字段         | 说明      | 录入方式 |
| ---------- | ------- | ---- |
| 深蹲 1RM（kg） | 一次性最大负重 | 数字输入 |
| 卧推 1RM（kg） | 一次性最大负重 | 数字输入 |
| 硬拉 1RM（kg） | 一次性最大负重 | 数字输入 |

**不填写三大项的替代方案：**

- 直接选择训练等级（新手 / 中级 / 高级），或跳过 → 按久坐人群处理

#### 2.2.4 目标设置（Onboarding 第 3 步）

| 选项  | 说明                    | TDEE 计算         |
| --- | --------------------- | --------------- |
| 增肌  | 在维持热量上增加 300-500 kcal | `维持 TDEE + 400` |
| 减脂  | 在维持热量上减少 300-500 kcal | `维持 TDEE - 400` |
| 维持  | 保持当前体重                | `TDEE × 训练系数`   |
| 自定义 | 手动输入每日目标 kcal         | 用户直填            |

#### 2.2.5 BMR / TDEE 计算规则（业务规则）

**基础代谢 BMR（Mifflin-St Jeor 公式）：**

```
男性: BMR = 10×体重(kg) + 6.25×身高(cm) - 5×年龄 - 5
女性: BMR = 10×体重(kg) + 6.25×身高(cm) - 5×年龄 + 161
```

**肌肉量修正系数（基于三大项 1RM 推算）：**

- 计算 `力量指数 = (深蹲 + 卧推 + 硬拉) / 体重`

- 力量指数 ≥ 6（男）/ 5（女）：`肌肉修正 = 1.08`

- 力量指数 ≥ 4.5 / 3.5：`肌肉修正 = 1.04`

- 其他：`肌肉修正 = 1.00`

- **修正后 BMR = BMR × 肌肉修正**

**活动系数（TDEE = BMR × 活动系数）：**

| 训练频率         | 活动系数  |
| ------------ | ----- |
| 久坐 / 极少运动    | 1.2   |
| 每周 1-3 次轻度   | 1.375 |
| 每周 3-5 次力量训练 | 1.55  |
| 每周 6-7 次高强度  | 1.725 |

#### 2.2.6 验收标准

- [x] 用户完成 Onboarding 流程后可立即看到自己的每日目标热量

- [x] 三大项三项全为 0 时，走普通 BMR 分支

- [x] 修改体重/身高后，BMR/TDEE 实时重新计算

- [x] 所有计算规则需展示在「关于 / 公式说明」页面（可追溯）

### 2.3 食谱推荐模块

#### 2.3.1 每日食谱生成逻辑

**输入：** 用户 TDEE、目标类型（增肌/减脂/维持）、PFC 偏好

**Step 1 — 分配 PFC 总热量占比**

| 目标 | 碳水     | 蛋白     | 脂肪     |
| -- | ------ | ------ | ------ |
| 增肌 | 45-55% | 30-35% | 15-20% |
| 减脂 | 30-40% | 35-40% | 25-30% |
| 维持 | 40-50% | 25-30% | 20-30% |

> 用户可在设置中自定义比例。

**Step 2 — 分配到各餐次**

默认分配：早餐 25% · 午餐 35% · 晚餐 30% · 加餐 10%（可调整）

**Step 3 — 食材填充（贪心 + 匹配度评分）**

对每餐的目标热量与 PFC，从食物库中选取若干食材组合使其最接近目标值。

#### 2.3.2 食材替换匹配算法（核心业务规则）

> 当用户点击某个食材的「替换」按钮时触发。

**匹配维度：**

1. **食物类别**（必须同组）：谷物 / 蛋白类（肉蛋鱼豆制品）/ 蔬菜 / 水果 / 乳制品 / 坚果 / 调料
2. **热量接近**：目标食材热量的 80% \~ 120% 区间内
3. **PFC 比例相似度**：计算向量余弦相似度
4. **用户偏好**：排除已标记「不喜欢」的食材，优先推荐「常用」

**相似度打分公式：**

```
score = α × cosine(PFC向量) + β × 热量接近度 - γ × 不喜欢惩罚

其中:
  PFC向量 = (碳水g, 蛋白g, 脂肪g) 归一化后
  热量接近度 = 1 - |候选热量 - 目标热量| / max(候选热量, 目标热量)
  α = 0.6, β = 0.4, γ = 100
```

**输出：** 返回 Top 3 候选替换食材卡片，附带每个的 PFC 对比与热量差值。

#### 2.3.3 验收标准

- [x] 生成的食谱每餐热量偏差 ≤ ±15%

- [x] 每餐 PFC 偏差 ≤ ±20%

- [x] 替换食材从点击到展示 ≤ 3 秒

- [x] 同一食材被用户 3 次标记「不喜欢」后，默认从推荐池剔除

### 2.4 饮食记录模块

#### 2.4.1 记录方式（极简）

| 方式   | 操作步骤                        | 适用场景     |
| ---- | --------------------------- | -------- |
| 一键入库 | 点击「今天就吃这个」→ 当日食谱全部标记已吃      | 默认 / 最常用 |
| 单餐确认 | 按餐次点击「已吃」                   | 吃了部分推荐   |
| 手动添加 | 搜食物 → 填克数                   | 吃了推荐外的   |
| 替换食材 | 在推荐卡片上点「换一个」 → 选替换 → 自动替换该餐 | 不想吃某食材   |

#### 2.4.2 每日汇总视图

- 顶部：环形进度条（实际摄入 vs 目标热量）

- PFC 三色条：碳水 / 蛋白 / 脂肪各自占比 + 克数

- 按餐次分组列表，每项支持修改克数 / 删除 / 替换

### 2.5 食物库模块

#### 2.5.1 数据来源

- 主数据源：[Sanotsu/china-food-composition-data](https://github.com/Sanotsu/china-food-composition-data)（《中国食物成分表》第 6 版）

- 字段：食物名称、类别、每 100g 的能量(kcal) / 蛋白质(g) / 脂肪(g) / 碳水(g)

#### 2.5.2 自定义食物

用户可创建自定义食物：

| 字段         | 说明                   |
| ---------- | -------------------- |
| 名称         | 品牌 + 商品名（如「桃李 全麦面包」） |
| 类别         | 从标准类别中选              |
| 每 100g PFC | 手动输入                 |
| 常用克数       | 默认值，减少记录时的输入         |
| 图片         | 可选，本地相册或拍照           |

#### 2.5.3 食物搜索

- 支持模糊搜索（如「面包」→ 命中所有含「面包」的条目）

- 支持按类别筛选

- 结果按「常用 > 收藏 > 标准库」排序

### 2.6 统计与反馈

- **周/月视图**：每日实际热量折线 + PFC 柱状

- **达成率**：目标完成天数 / 总天数

- **AI 建议（可选）**：后端对接大模型，生成一段针对本周饮食的简短建议（≤ 100 字）

## 四、非功能性需求

| 维度   | 要求                                              |
| ---- | ----------------------------------------------- |
| 性能   | 首页加载 ≤ 1.5s；搜索 ≤ 500ms；替换推荐 ≤ 1s                |
| 可用性  | 食物库、用户基础信息支持离线缓存；推荐/替换算法前端可降级（后端挂了走本地简化逻辑）      |
| 安全   | 所有接口 HTTPS；用户 openid 脱敏存储；自定义食物图片可走公开 CDN（不含隐私） |
| 可扩展性 | 食物库数据可一键导入更新；PFC 比例 / BMR 公式版本化                 |
| 兼容性  | 微信 ≥ 8.0；iOS ≥ 13；Android ≥ 8                   |
| 埋点   | 关键事件（登录、生成食谱、替换食材、标记不喜欢）均上报，用于后续推荐效果评估          |
