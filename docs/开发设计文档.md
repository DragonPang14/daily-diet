## 三、前端启动与鉴权策略

### 3.1 核心原则：登录不阻塞首页

- **默认启动页**：`pages.json` 中 `pages[0]` 设置为 `pages/home/index`（tabBar 首页），应用启动后直接进入
- **App.vue 静默登录**：`onLaunch` 中后台尝试 `uni.login` → `authApi.wxLogin(code)`，成功存 token，失败（网络/后端/非微信环境）静默忽略，**不阻塞首页渲染**
- **新用户引导**：登录成功且后端返回 `isNewUser: true` 时，App.vue 主动 `reLaunch('/pages/onboarding/index')` 进入引导；老用户和登录失败均跳过引导直接进首页
- **Onboarding 页面职责**：仅承载 Step 1-3 的引导表单（基础信息 / 训练水平 / 目标设置），不再负责触发登录。登录已在 App.vue 前置完成，进入本页时用户一定是已登录新用户

### 3.2 页面权限策略（三级）

| 级别 | 代表页面/操作 | 未登录行为 |
|------|--------------|-----------|
| 公开 | 食物库浏览、首页概览 | 正常渲染，公共接口无鉴权 |
| 弱鉴权 | 饮食记录列表、食谱查看 | 允许渲染，数据接口 401 时显示占位空态 |
| 强鉴权 | 生成食谱、提交记录、修改个人信息、Onboarding 引导 | `isLoggedIn()` 校验，未登录时业务层提示引导登录 |

### 3.3 HTTP 客户端行为

- **Token 注入**：`src/api/http.ts` 的 `buildHeader()` 从 storage 读 token，有则自动注入 `Authorization: Bearer <token>`，无则跳过
- **401 处理**：仅清除本地 token（调 `store.logout()`），**不强制跳 Onboarding**。由业务页面在自身逻辑中按需决定是否引导登录
- **公共接口无鉴权**：食物库搜索等 `/foods` 系列接口后端不校验 JWT，前端无 token 时也能正常请求

### 3.4 启动时序图

```
uni-app 启动
    │
    ▼
pages.json 解析 → 默认页面 home/index
    │
    ▼
App.vue onLaunch  ──────── 后台静默登录 ────────┐
    │                                            │
    │  (并行) 页面实例化 & 渲染 home/index        │
    │                                            │
    ▼                                            ▼
首页数据加载            登录结果返回
    │                    │
    │                    ├── 成功 + isNewUser
    │                    │     → reLaunch onboarding

    │                    │

```

## 四、核心业务流程设计

### 4.1 BMR / TDEE 计算流程

```
请求到达
    │
    ▼
UserController.calculateTarget(userId)
    │
    ▼
UserService.calculateTarget(user)
    │
    ├── BmrCalculator.mifflinStJeor(gender, weight, height, age)
    │         → 返回 BMR
    │
    ├── MuscleEstimator.correct(user)
    │         │
    │         ├── if 三大项全为 null/0 → 返回 1.0
    │         └── else 计算 strengthIndex
    │              strengthIndex = (squat + bench + deadlift) / weight
    │              if ≥ threshold → muscleFactor = 1.08 / 1.04 / 1.00
    │         → 返回 muscleFactor
    │
    ├── correctedBmr = BMR × muscleFactor
    │
    ├── activityFactor = 根据 training_level 查表
    │
    ├── tdee = correctedBmr × activityFactor
    │
    ├── 应用 goal_type 偏移 (±400 kcal 或 user.custom_tdee)
    │
    ├── 【PFC 比例初始化】
    │      if 本次 Onboarding / 目标变更，且用户未手动覆盖过 PFC：
    │        goal_type → 默认 PFC 映射表（取中值）
    │          增肌 (1) → 45/32/23
    │          减脂 (2) → 35/37/28
    │          维持 (3) → 45/28/27
    │          自定义 (4) → 不覆盖，保留用户手填值
    │        → 写入 user.pfc_carbo_pct / protein_pct / fat_pct
    │
    └── 更新 users 表 bmr / tdee / muscle_factor / pfc_*_pct → 返回
```

### 4.2 每日食谱推荐引擎

```
RecipeService.generateDaily(user, date)
    │
    ├── 1. 确定当日目标
    │      targetKcal = user.tdee（或 user.custom_tdee）
    │      targetPFC = (user.pfc_carbo_pct%, user.pfc_protein_pct%, user.pfc_fat_pct%)
    │      （注：PFC 比例已在 4.1 初始化完成，这里直接读用户字段，不再二次映射）
    │
    ├── 2. 分配到餐次
    │      meals = {
    │        早餐: 0.25 × target,
    │        午餐: 0.35 × target,
    │        晚餐: 0.30 × target,
    │        加餐: 0.10 × target
    │      }
    │      （比例可在用户配置中覆盖）
    │
    ├── 3. 各餐次调用 RecommendationEngine.fillMeal(mealTarget, user.id)
    │
    │      fillMeal 内部:
    │        │
    │        ├── a. 确定该餐所需的食物类别（至少：1 蛋白 + 1 主食 + 1 蔬菜，按餐次不同调整）
    │        │
    │        ├── b. 对每个类别:
    │        │      从 foods 表中筛选:
    │        │        - category 匹配
    │        │        - 排除 food_dislikes
    │        │        - 排除历史上用户高频拒绝的
    │        │
    │        ├── c. 贪心组合: 不断挑 PFC 向量最能弥补剩余缺口的食物
    │        │      （可用 scipy/自研简化版，单体场景下 10~20 种候选 ≈ 毫秒级）
    │        │
    │        └── d. 算克数使组合热量逼近 mealTarget
    │
    └── 4. 写入 daily_recipes + recipe_items → 返回
```

### 4.3 食材替换算法

```
SubstitutionMatcher.findCandidates(foodId, user.id, topN=3)
    │
    ├── 1. 查原食物 originalFood
    │
    ├── 2. 过滤候选集
    │      SELECT * FROM foods
    │      WHERE category = originalFood.category
    │        AND energy_kcal BETWEEN originalFood.energy_kcal * 0.8
    │                          AND originalFood.energy_kcal * 1.2
    │        AND id NOT IN (SELECT food_id FROM food_dislikes WHERE user_id = ? AND dislike_count >= 3)
    │        AND id != originalFood.id
    │
    ├── 3. 打分（并行流处理）
    │      for candidate in candidates:
    │        cosine = cosineSimilarity(originalFood.pfcVector, candidate.pfcVector)
    │        calClose = 1 - abs(candidate.energy_kcal - originalFood.energy_kcal)
    │                   / max(candidate.energy_kcal, originalFood.energy_kcal)
    │        dislikePenalty = 查 food_dislikes 中该 user 对 candidate 的 dislike_count
    │        score = 0.6 * cosine + 0.4 * calClose - 100 * (dislikePenalty > 0 ? 1 : 0)
    │
    └── 4. 取 Top N → 返回
```

**PFC 向量余弦相似度实现：**

```java
public double cosineSimilarity(Food a, Food b) {
    double[] va = normalize(new double[]{a.getCarboG(), a.getProteinG(), a.getFatG()});
    double[] vb = normalize(new double[]{b.getCarboG(), b.getProteinG(), b.getFatG()});
    double dot = va[0]*vb[0] + va[1]*vb[1] + va[2]*vb[2];
    return dot; // 已归一化，cos ∈ [0,1]
}
```

## 五、API 接口定义

> 基础路径：`/api`
> 鉴权：请求头 `Authorization: Bearer <JWT>`，登录接口除外
> 返回格式：`{ code: 0, data: {...}, msg: "" }`
> **版本标注**：每个接口标注了首发版本，帮助前后端明确里程碑边界
> **日期参数时区约定**：后端统一按服务端所在时区处理（北京时间 UTC+8）。`today`、`record_date` 等日期字段均按服务端本地零点切分；前端不传时区，只传 `yyyy-MM-dd` 字符串

## 十、测试策略

### 10.1 分层目标

| 层 | 目标覆盖率 | 重点测试内容 |
|----|-----------|------------|
| 单元测试 (Unit) | ≥ 80% | BMR/TDEE 计算、食物替换打分、PFC 向量余弦相似度、推荐引擎的贪心填充 |
| 集成测试 (Integration) | ≥ 60% | REST API 契约、MyBatis-Plus 数据访问、Redis 缓存、食物数据导入 |
| 端到端测试 (E2E) | 关键路径全覆盖 | Onboarding → 生成食谱 → 一键入库 → 替换食材 → 标记不喜欢 → 推荐排除 |

### 10.2 后端单元测试栈

- **框架**：JUnit 5 + Mockito
- **被测对象**：放在 `algorithm/` 包下的纯算法类（不依赖 Spring 容器）
- **示例**：
  - `BmrCalculatorTest` —— 覆盖男女、边界年龄/身高/体重
  - `MuscleEstimatorTest` —— 三大项全空、刚达标、远超阈值
  - `SubstitutionMatcherTest` —— 同一类别/不同类别/热量超出 ±20%/PFC 接近度/dislike_count 过滤
  - `CosineSimilarityTest` —— 相同向量 → 1；正交向量 → 0；反向 → -1

### 10.3 后端集成测试栈

- **框架**：`@SpringBootTest` + Testcontainers（起 MySQL + Redis 容器）
- **重点**：
  - `UserApiIntegrationTest` —— PUT `/users/me` 后 GET 确认 BMR/TDEE 已重算
  - `RecipeApiIntegrationTest` —— GET `/recipes/today` 验证返回结构 + 食材 PFC 偏差 ≤ ±20%
  - `RecordApiIntegrationTest` —— POST bulk 后 GET summary 验证汇总正确

### 10.4 前端测试栈

- **框架**：Vitest + Vue Test Utils（组件测试）
- **E2E**：Playwright（针对 H5 构建产物跑端到端）
- **重点**：
  - Onboarding 三步导航 + 校验规则
  - 首页推荐卡片渲染 + 替换弹层交互
  - 每日汇总环形进度条

### 10.5 GitHub Actions 中的测试步骤

  run: mvn verify -B -Pintegration

    MYSQL_PASSWORD: ${{ secrets.MYSQL_ROOT_PASSWORD }}

## 十一、安全与数据治理

| 项 | 方案 |
|----|------|
| HTTPS | Nginx 配置 Let's Encrypt / 阿里云免费证书，自动续签 |
| 鉴权 | JWT (RS256)，access token 2h + refresh token 7d |
| 密码 | 不涉及（微信登录）；后台管理登录走独立 Spring Security |
| 敏感数据 | openid 仅存 hash？不，openid 本身非敏感，直接存；手机号/昵称按微信规范获取 |
| SQL 注入 | MyBatis-Plus 参数化查询；禁止 `${}` 拼接 |
| XSS | 前端输入校验；后端对 nickname 等用户输入做 HTML 转义 |
| 限流 | Redis + Bucket4j 对 `/auth/wx-login`、`/recipes/generate`、搜索接口限流 |
| 数据备份 | MySQL 每日快照 + binlog；数据卷定期上传 OSS |
